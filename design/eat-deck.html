Goal: lower the two-qubit depth of compiled circuits — what hurts most on real hardware — without breaking correctness or inflating gate count.

The starting point

What Sabre does, and where it left depth on the table

Sabre is Qiskit's router: it picks an initial layout (which logical qubit goes where) and then routes — inserting swap gates so every two-qubit gate lands on physically-connected qubits. Swaps add depth. Sabre tries several random layout trials, routes them, and keeps the best.

what we optimize — depth (D2)

The score pushes down two-qubit depth: how many layers of 2-qubit gates run in series. It's what limits circuits on today's noisy hardware.

what we protect — gate count (N2) + correctness

The obvious cheat is to cut depth by adding swaps — fewer layers, but more gates. So 2-qubit gate count can't regress (a hard guard), nor can correctness, compile time or memory. Depth only counts if nothing else gets worse.

The untouched levers the agents went after: how ties break, what trials are scored by, how far the router looks ahead, and where routing effort is spent — each iteration takes one.

ITER 11.066

Make the tie-breaks depth-aware

optimizer

Why one agent: with no idea yet where depth is lost, the cheapest move is a single agent that diagnoses and takes the one safe win.

before

When several swaps or layout trials score equally, Sabre broke the tie by arbitrary order — whichever came first.

after

Among the equally-scored options, pick the one that adds the least two-qubit depth. Same options considered, smarter pick.

↓ 6.2% depth. Safe by construction — it only reorders already-equal choices, so it can't cost gate count.

ITER 21.125

Pick better layout trials, cheaply

routerlayoutintegrator

Why 3 agents: iter 1 only touched tie-breaks. Split the problem by stage — router + layout exploring in parallel — with an integrator that owns timing and is the only one allowed to ship.

before

Layout trials were ranked by swap count, and every trial got a full, expensive routing pass — effort spread thin across all of them.

after

Rank trials by a depth estimate instead, and screen: route every trial once cheaply, then fully route only the best four. Effort goes where it matters.

↓ 11.1% depth. The integrator also rejected two of its own team's candidates (thin evidence; a risky cap for +0.75%) — the discipline that keeps the score honest.

ITER 31.250

Give the basic router real lookahead

routerlayoutintegrator

Why the same team: the structure worked, so the supervisor changed the targets, not the roles — aim at the weakest router and the families with the most headroom left.

before

Qiskit's level-0 ("basic") router was nearly greedy — it took the locally-best swap with little sense of what came next.

after

A real lookahead heuristic — lookahead + decay + a depth window — fed by halving-and-refinement of the layout trials. Both explorers' work merged into one change.

↓ 20% depth — the biggest single jump of the run, and EAT's clearest act of combining two agents' ideas.

The turn

Was it real — or was it learning the test?

The score was climbing on the panel the agents can see. A held-out check — circuits they never train on — gave the uncomfortable answer.

Iteration 3 quietly made 8 circuits worse on the held-out set — up to +10% worse. Classic over-fitting. The supervisor was told. What it did next is the most interesting part of the run.
ITER 4re-aimed

Build a team to catch yourself cheating

auditormechanicintegrator

Why a new kind of team: the goal itself changed. Add an auditor whose only job is to build a held-out suite the others never see, map every regression, and blame each on a specific mechanism.

the goal until now

"Raise the dev score." Which, unchecked, rewards tuning to the circuits the agents can see — the over-fitting the turn exposed.

the goal from here

"Stop over-fitting." Explicit target: at least halve the held-out regressions. The mechanic repairs the named weak clusters while holding the score.

The run turned from score-chasing to robustness. (Real work — scored 0 only by a cluster-evaluator bug, recovered later.)

ITER 5–61.297

Spend extra routing only where it pays

layoutrouterintegrator

Why these fixers: explorers-plus-gatekeeper again, but each pointed at a named weak cluster the auditor found, owing a study of where depth is lost and a principled fix.

before

The chosen layout got a fixed amount of routing effort — take it or leave it, no second look even when a circuit might benefit.

after

One extra routing-trial batch for the chosen layout — but kept only if it beats the incumbent on both swap cost models. Extra compute spent only when it clearly pays.

↓ 22.9% depth — and it did it while generalising better (next slide).

ITER 10 · new best1.329

One cause, one file, six lines

layoutrouterintegrator

Why this team: a fresh supervisor split the Sabre pass by stage — one agent owning layout (where qubits start), one owning routing (which swaps get inserted), and an integrator acting as maintainer-reviewer and the only agent allowed to change the shared tree. Each was told to find one localized, explainable cause and fix it like a real pull request.

before — the diagnosis

The layout search runs a trial as alternating forward/back routing passes that all share one seed — so once a pass returns to a layout it already tried, the trial is stuck in a limit cycle, repeating itself. The agent measured it: this happened in 55–64% of refined trials at the higher opt levels, burning the whole patience budget going nowhere.

after — the fix

When a trial revisits an earlier layout, draw a fresh routing seed and keep exploring instead of spinning. That's the entire change: +6 lines in layout.rs — no new constants, no tuning, no change to scoring or selection.

1.329037 — PASS, new best. The single most localized, explainable improvement of the whole run — and exactly the shape of change a Qiskit maintainer could merge on its own.

Did it cheat? — depth vs gate count

Fewer layers and fewer gates

If the agents had bought depth by adding swaps, the blue bars (depth) would grow while the gate-count bars stayed flat or rose. Instead, at iteration 9, both drop at every optimization level — genuinely better routing, not a trade.

Independent benchmark — IBM Benchpress

The win holds on a suite we never trained on

The dev panel and the held-out set are both our circuits. Benchpress is IBM's own public transpiler benchmark — different circuits, different metrics, run by its harness. We compiled 18,738 circuits (both optimization levels, 3 seeds) on the 1.323 tree vs. baseline. An A/A control confirmed the measurement is exact.

This settles the "did it cheat?" question independently: on an outside benchmark, depth and gate count both fall and runtime doesn't regress — genuine routing, not swap-padding. Honest edge: end-device fidelity (ESP) improves only modestly (~+0.8% on gate errors) and is roughly flat on idle-decoherence — the circuits are cheaper to run, but the success-probability gain on a modeled chip is small, not another 6%.

ITER 7–8lock

Stop, verify, and lock it in

stewardfinisher
Why this team

Back to a single agent — twice. The supervisor judged the gains had peaked for this budget and that the real risk was now shipping something unverified.

What they did

No new optimization. One steward ran the full official harness on the best tree; one finisher made sure exactly that verified tree is what ships — with a fallback plan if the top candidate didn't fully pass.

Result

The 1.297 solution confirmed and locked — the endpoint of the first run, and the base the continuation (iteration 9) then built on.

What the arc shows

The team was never fixed

1 agent→3→ audit team→fixers→lock→resume (1.323)→stage-split (1.329)

The supervisor's intent moved with the problem: find anything → question the heuristic → stop over-fitting → verify and lock → resume and push. The shape of the team was itself a decision, remade every round.

The clearest result isn't any single score — it's that feedback changed behavior. Told it was over-fitting, it restructured its own team and produced solutions both higher-scoring and more robust on circuits it had never seen. The score rose every iteration: 1.066 → 1.125 → 1.250 → 1.297 → 1.323 → 1.329.

Honest footnotes: development-panel scores, one task and metric; the best solution still makes 2 of ~400 held-out circuits slightly worse.
